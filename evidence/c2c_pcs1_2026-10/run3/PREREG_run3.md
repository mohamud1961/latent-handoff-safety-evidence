## Pair (fixed now)

Receiver `Qwen/Qwen3-0.6B`, sharer `Qwen/Qwen3-4B`, released **general** fuser `nics-efc/C2C_Fuser/qwen3_0.6b+qwen3_4b_Fuser/final` (28 projectors, 1059 MB; config run name "0.6B+4B_C2C_general_OpenHermes_500k"; source 8 KV heads x 128 -> target 8 x 128; receiver layer i reads sharer layer i+8; same tokenizer and chat template, `is_do_alignment: false`). Not the GSM8K-specific fuser (`qwen3_0.6b+qwen3_4b_gsm8k_Fuser`). fp16 on one T4: 8.04 + 1.2 + 1.06 = about 10.3 GB of 15 GB.

**Paper numbers for this pair.** Table 9 of arXiv 2510.03215 (Sharer Qwen3-4B, Receiver Qwen3-0.6B, default C2C fuser; we assume it is the released general fuser, which the config name supports but the paper does not state): OpenBookQA receiver 39.20, sharer 79.40, text-to-text 46.40, **C2C 55.20**; ARC-C 41.04 / 87.48 / 52.00 / 60.17; MMLU-Redux 35.53 / 71.38 / 42.95 / 45.92; C-Eval 32.04 / 68.09 / 36.96 / 44.40. Table 15 (GSM8K: single model 41.17, C2C 62.55) uses the task-specific GSM8K fuser, so it is **not** a reference for the numeric task here, which uses the general fuser.

## Part A: plumbing (changed back toward `PREREG.md`)
Receiver, sharer, C2C, and mismatched-sharer C2C (K=1, generation readout only) on the 200 OBQA items, generation readout (<= 64 tokens, C2C `extract_answer_from_content`) and logit readout. **Plumbing OK** iff all hold: (i) no non-finite logits (counted at the end of Part A; Part B's count is reported too and any non-finite item is excluded from every comparison); (ii) projection-off C2C matches the plain receiver's argmax on >= 95% of items; (iii) C2C beats the receiver under the generation readout with a paired-bootstrap 95% CI excluding 0 (the paper reports a +16 pt gain for this pair, so the original criterion is restored); (iv) generation parse rate >= 90% for R, S, C and C_mm_gen. Informational, not a criterion: whether the paper's OBQA numbers (R 39.2, S 79.4, C 55.2) lie inside our 95% CIs for R, S and C (CI half-width is about 6-7 pts at N = 200). If a criterion fails, Part B is flagged uninterpretable as in `PREREG.md`, but everything is still run and reported.

## Safeguard 1: several wrong states per question (Part B)
For every item C2C is also run with the sharer cache computed on **K = 3 different wrong-question prompts** of exactly the same receiver-template token length (C_mm,0, C_mm,1, C_mm,2). Partners are drawn from the 7276 loaded MMLU-Redux / ARC-C / OBQA prompts, never the item itself, with distinct token sequences, without replacement, by a per-item seeded shuffle (`Random("0:mmK:<item id>")`), so the three wrong states differ. The receiver always sees the real prompt. Items lacking 3 such partners are excluded from the primary comparisons; the coverage is reported (items with fewer partners keep whatever partners they have; they enter only secondary analyses). "All items" below means all scored items with all K partners ("K-complete").
- **Primary quantity: Delta_specific = acc(C) - mean_k acc(C_mm,k)** on K-complete items, paired by item (per-item difference 1[C correct] - mean_k 1[C_mm,k correct]), paired bootstrap 95% CI. Also on D.
- Reported with it: acc(C) - acc(C_mm,k) for each k with CIs; per-item answer agreement C vs C_mm,k for each k (all items, D, cells A / B / W) with CIs and mean |dprob|; the spread across k (range and SD of acc(C_mm,k), range of the per-k differences, pairwise agreement among the wrong states); the same after calibrating both (each C_mm,k by its own cross-fit prior).
- **Calibrated-receiver baseline kept:** acc(C) - acc(Rcal) on all scored items and on D; acc(Ccal) - acc(Rcal); Delta_specific_cal = acc(Ccal) - mean_k acc(C_mm,k,cal).

## Safeguard 2: a non-letter task (numeric exact-answer generation)
**Task: GSM8K** (`openai/gsm8k`, `main`, test split), through C2C's own evaluator path: C2C's prompt template (`UnifiedEvaluator._format_math_problem_example`, copied and checked for byte equality by `validate_notebook.py`), gold parsed as `UnifiedEvaluator.parse_answer` does (the number after `####`), chat template with thinking off, and C2C's own grader `rosetta.utils.matheval.GSM8KEvaluator.rule_judge` (math_verify 0.8.0, latex2sympy2-extended 1.10.2, as pinned in C2C's `environment.yml`) for exact-match correctness. C2C supports GSM8K in its evaluator (`DATASET_CONFIGS["gsm8k"]`), so no fallback task is needed. If the grader cannot be imported, the numeric task is marked unavailable and logged (the MC parts still run); MATH-500 is not substituted.
- Greedy, no sampling, `max_new_tokens = 320` for every condition (a cap chosen for runtime; solutions longer than that are truncated for all conditions alike and count as wrong or unparsed). Receiver and sharer alone are generated through HF `generate`; C2C through `RosettaModel.generate`, fusing all prompt tokens but the last (the README / evaluator pattern, as in Part A).
- **Items.** The GSM8K test prompts (<= 1536 tokens) are grouped by exact receiver-template token length. Groups with >= 2 items (capped at 8 items) are shuffled by seed (`Random("0:numgroups")`) and queued until at least N = 300 items are queued. **Within a group, the wrong-question partner of item j is item j+1 (cyclic shift: a derangement, nobody is their own partner), so the partner's sharer answer is also computed, which the leak check needs.** Items in a group of equal length are generated as one batch for R and S (no padding, so the numerics are those of unbatched generation); C and C_mm are generated one at a time.
- **Conditions:** R, S (fed the tokens the fuser feeds it), C (real sharer cache), C_mm (K = 1, the sharer cache of the partner prompt).
- **Size and time rule.** Target N = 300 queued items; groups are processed whole, in the queued order. After 50 minutes of numeric time the run stops at the next group boundary **provided at least 120 items are done**, and in any case at 185 minutes since notebook start. The N actually achieved is reported; N < 300 is logged as a deviation of the numeric task's size, not of any control. Controls are never reduced; N is.
- **Metrics (paired bootstrap 95% CIs over items).**
  - Exact-match accuracy of R, S, C, C_mm; C - R, C - S, C - C_mm, C_mm - R; fraction of items where C and C_mm give the same final number.
  - **Numeric inheritance:** on items where S produced a number, P(C's number == S's number) vs P(C_mm's number == S's number for the real question), and the paired excess; also on the subset where S is wrong, and where S is wrong and R's number differs from S's (numbers equal if within 1e-6 relative).
  - **Leak check:** P(C_mm's number == the partner's sharer number) vs P(C_mm's number == the sharer number of a random item of a different length, seeded), and the paired excess; also on items where the partner's sharer answer is wrong. A leak excess with lower CI > 0 means the wrong-question cache's content shows up in the receiver's answer; it is reported, and read as a property of the control, not as success of the bridge.
- **Numeric verdict (decision input):** *positive* iff the lower CI of acc(C) - acc(C_mm) > 0; *negative* iff the upper CI < 0; *null* otherwise; *unavailable* if N < 60 or the task did not run.

## Safeguard 3: planted false belief (Part C) is kept
As in `PREREG.md` (500 items from Part B; a random wrong letter planted as a "Reference note" the sharer sees; the receiver sees masked padding of equal length; control note with "X"; Delta_bridge on items where the sharer itself adopted the planted letter; text handoff as reference; lower CI of Delta_bridge >= 0.05 means the bridge carries sharer-private information). The Qwen3-4B sharer is expected to adopt the plant more reliably than the earlier sharers. Part C runs after Part B and before the numeric task; it is dropped only if (minutes since notebook start) + (its measured-timing estimate) > 170 min, and that would be logged.

## Safeguard 4: checks kept from run 2
Strict projector key check (no missing or unexpected keys) and finiteness check of the cast fuser weights; fp16 on the T4 gated against an fp32 reference (finite; argmax agreement >= 0.80; mean |dprob| <= 0.10 on R, S and C). **The fp32 reference runs on the CPU** (the fp32 stack is about 20.6 GB and does not fit the GPU) on 16 probe items (cap 10 min, >= 8 needed); it is attempted only if at least 23.6 GiB of host RAM (min of `/proc/meminfo` and the cgroup limit) is available, because a CPU out-of-memory kill would lose the run. If no usable reference exists, fp16 is accepted on finiteness alone and logged as a deviation (Part A's sharer accuracy against the paper's 79.4 then serves as a sanity check on the 4B in fp16); if fp16 fails the gate the run falls back to bf16 (emulated on a T4) and logs it. Also kept: projection-off == receiver (Part A), equal-length assertions on every C2C call, `S_nat` is not recomputed when the sharer's own template yields identical tokens (it does for Qwen3 -> Qwen3), and the time-budget shrink: if the estimated A + B compute exceeds 110 min, Part B's pool is shrunk (floor 600 items, pre-registered order) and logged.

## Decision rule (fixed now)
Notation: Delta = Delta_specific (MC, K-complete items); "beats calibrated R" = lower CI of acc(C) - acc(Rcal) on all scored items > 0; numeric verdict as defined above.

| Outcome | Condition |
|---|---|
| **Content-specific communication** | lower CI of Delta >= +0.02 **and** C beats calibrated R **and** numeric verdict *positive* (lower CI of acc(C) - acc(C_mm) on GSM8K > 0) |
| **Partial: "some genuine transfer; accuracy overstates it"** | not content-specific, and either the lower CI of Delta > 0 (so 0 < lower CI < +0.02, or the MC criteria hold without numeric corroboration, or C does not beat calibrated R) or the numeric verdict is *positive* while MC is not content-specific (the tasks disagree). Reported with the magnitudes of Delta and of the numeric C - C_mm. |
| **Non-specific** | the 95% CI of Delta includes 0 **and** calibrated R is within 2 pts of C (point estimates, |acc(C) - acc(Rcal)| <= 0.02), and the numeric verdict is not *positive* |
| anything else | **Mixed / no claim** |

Rows are evaluated in this order (content-specific, partial, non-specific, mixed). The "within 2 pts" clause is a statement about point estimates (an equivalence test at +-2 pts is not resolvable at N ~ 2000: the paired CI half-width is about 2-2.6 pts when two conditions disagree on 30-40% of items); the CI is reported beside it. For scale: in runs 1 and 2 C and C_mm agreed on 97% of items and the CI of C - C_mm on all items was about +-0.7 pts, so a +0.02 lower CI needs a true effect of about 3 pts.

**Belief-transfer table (carried over, unchanged; E_A, E_B, E_W computed with C_mm,0 as the null):**
| Outcome | Meaning |
|---|---|
| lower CI of E_B >= 0.10 | **Belief transfer**: the receiver abandons a correct answer for the sharer's wrong one beyond the null. |
| E_B upper CI < 0.10 and E_A >= 0.10 | **Truth-biased helper**: follows the sharer only when it is right. |
| E_A, E_B CIs inside +-0.05 and the paired CI of acc(C) - acc(C_mm,0) on D includes 0 | **Non-specific perturbation**. |
| anything else | Mixed or underpowered; no claim. |

The run's headline is the decision rule above (MC + numeric); the belief-transfer table and Part C answer the separate belief question, and all are reported even if they disagree. Anything not listed in this file is **post-hoc** and will be labelled as such in `RESULTS_run3.md`. No multiplicity correction is applied.

## Known limits (stated before the run)
One pair, one fuser (trained on identical inputs only, so wrong-question and planted inputs are out of distribution; the paper does not say whether Table 9's fuser is this release); the numeric task is small (N about 150-300 because C2C generation cannot be batched, so the CI of C - C_mm on it is about +-3-6 pts) and capped at 320 new tokens; the MC readout is letter logits (the numeric task and Part A's generation readout are the non-logit checks); the fp32 gate reference is a 16-item CPU sample (or absent, see above); Kaggle T4 wall time is capped by the plan below. A null would not refute latent communication in general; it would show that on this strong-sharer pair a wrong-question control, a calibrated receiver and a non-letter task still do not credit the bridge with content-specific communication. A positive would be the first evidence in this audit that the bridge carries question-specific content.
